# UI tool feedback and evidence delivery

Scope: the extracted Calendar inspector, tested on one Linux-emulator task.
This guidance is not a model-wide capability conclusion or a new permission.

- Check the current hierarchy after keyboard/window changes. The same screen
  coordinate can select another action after a layout shift; record intended
  control, actual input and displayed output before claiming passage.
- A tool's non-error wrapper can contain `Invalid parameters`. Inspect command
  output and CLI usage, then verify the changed field. An unsupported symbolic
  key name is a tool-contract discovery problem; it is not proof that editing is
  impossible. Numeric key alternatives depend on the actual tool contract.
- A repeated successful integer-evaluation click does not count as operating an
  original example button. Record the control identity, not only the coordinates.
- Deliver evidence incrementally. A valid sixth observation may exist in the
  captured tool trajectory while the student's summary lists only five. Preserve
  that difference: the controller can verify observed progress independently,
  while incomplete/stale delivery remains a separate finding.

Use minimal help only after an observed barrier; record actual content and types.
Mechanical source restoration belongs before participant budget, with byte
verification. Supplied prior source is not new independent implementation.
